# 工程通则（第 2 层 · 与语言无关的工程素养）

适用于所有语言与仓库的、具体的现代工程实践。第 1 层（`AGENTS.md`）约束行为，本层约束工程素养，
`languages/*.md`（第 3 层）补充各语言的惯用法。仓库自身的规则与更就近的配置，优先级高于本文件。

良好的工程遵循一条工作弧——**理解与设计 → 实现 → 验证 → 集成 → 发布 → 运维**——每个阶段都有需
先达标才能进入下一阶段的门槛。末尾列出的关注点（安全、依赖、性能、文档）是**横切**的：贯穿每个阶
段，而非只属于某一个。仪式繁简可随影响大小而定，但不可跳过任何阶段。

## 1. 理解与设计（动手之前）

- 在写代码之前，先界定问题、并写下「完成」的样子——即验收标准。若需求含糊或影响重大，先把它厘清。
- 研究既有系统、约束与约定。至少权衡两种方案及其明确取舍；选择能满足需求的最简者（YAGNI），
  为「变化」而设计，而非为臆想的未来而设计。
- 先设计接口与契约。让单元小而单一职责、高内聚、低耦合；让核心逻辑保持纯粹，把副作用推到边缘。
- 把重大或难以回退的决策，在**做出决策的当下**记为简短 ADR，连同你否决的备选及理由。

## 2. 实现

- 遵循既有约定、模式与结构；与周边风格保持一致。
- 改动保持最小、兼容、可回退。不做与任务无关的顺手重构、重命名或重新格式化。
- 一次提交只做一件逻辑上的事，提交信息用祈使句并说明「为什么」。绝不提交机密、凭据、构建产物或大型
  二进制文件；维护好 `.gitignore`。在分支上工作；不重写或强推共享历史。
- 写自解释的代码。注释意图、不变量与取舍——而非显而易见之事。

## 3. 验证（测试）

- 一项改动只有在「能构建、格式化 / 静态检查 / 类型检查无告警、测试通过、文档与注释已随之更新」时，
  才算**完成**。
- 测试行为与契约，而非实现细节。测试必须确定、隔离、快速——不依赖墙钟时间、网络、执行顺序或共享可变状态。
- 遵循金字塔：大量小型单元测试，较少集成测试，少量端到端测试。把逻辑下沉到便于廉价测试之处。
- 修复缺陷应先写一个针对旧行为会失败的测试。不要靠删除或 `skip` 测试来让 CI 变绿——修根因，或书面说明
  跳过的理由。覆盖率是信号而非目标：先覆盖高风险与承重的部分。

## 4. 集成（CI）

- 每次改动在合入前都经过同一道关卡：**格式化 → 静态检查 → 类型检查 → 测试 → 构建**。快速且明确地失败。
- 本地与 CI 使用同一套命令。固定工具链与依赖版本，使构建可复现。让流水线快到人们真的愿意运行。

## 5. 打包与发布

- 从一次干净的构建中产出单一、带版本、可复现的产物——在工具链允许处做到确定、封闭。只装进必要之物；
  绝不打包机密或开发期杂物。
- 对外被依赖的一切采用**语义化版本**，并维护面向用户的变更日志。不在没有大版本号提升与迁移说明的情况下
  破坏公共接口。
- 在产物离手之前，校验其完整性与来源（校验和 / 签名）。

## 6. 交付与运维

- 以小而可回退的增量发布，并保留回滚路径；高风险改动优先渐进式放量。
- 配置取自环境、与代码分离，并在启动时校验——遇缺失或非法值即快速失败。提供安全默认值；为每个必需变量
  编写文档。
- 让系统可观测：以合适级别记录结构化日志（绝不含机密或隐私数据），并为服务补充指标、链路追踪与关联 id，
  使一次请求可被追踪、一次故障可在生产中被诊断。
- 绝不静默吞掉错误。要么处理，要么带上上下文向上传播；在失败要紧之处明确失败。错误信息应说清：
  哪里失败、为何失败、下一步该怎么办。

## 横切关注点（贯穿每个阶段）

- **安全。** 机密来自环境或密钥管理器——不进源码、日志或仓库。对每个凭据与作用域遵循最小权限。
  在信任边界做校验与编码；把一切外部输入视为有敌意；用参数化查询，绝不字符串拼接 SQL 或 shell；
  在每条受保护路径上强制鉴权与授权。对触及认证、数据或对外接口的改动做威胁建模，并保持依赖已打补丁。
- **依赖与供应链。** 提交锁文件并固定版本——可复现的安装优先于「latest」。只有在权衡了维护活跃度、
  许可证、传递依赖体量与安全性，并与「自己实现」作比较之后，才引入某个依赖；优先标准库。审计已知漏洞，
  对敏感内容校验完整性。
- **性能与资源。** 先正确，再优化；优化前先度量；优化经证实的热点。即便如此，也别写出可避免的平方级
  复杂度、N+1 查询，或循环里无谓的分配。对获取的每个资源确定性地释放；对外部调用设置超时与上限，
  对一切无界之物施加背压。
- **文档。** 一份说清「它是什么、为何存在、如何运行与测试」并保持更新的 README。重大决策在贴近代码处
  以 ADR 记录。记录不直观之处——意图、不变量、取舍——而非显而易见之事。
