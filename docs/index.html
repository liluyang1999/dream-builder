01 · Product snapshot

当前项目究竟是什么

Dream Builder Fantasy Tree 的玩家名称是《智慧树之森》。它已从“可旋转观察的程序化智慧树” 演进为一个单人、离线、第三人称卡通森林盒庭：玩家探索三条支路，收集三枚光种，阅读森林记忆， 完成四拍方向净化，并看到中央智慧树、光照、地表、音景和章节门一起复苏。

  • 体验闭环标题、继续/新游戏、暂停、设置、章节结尾、继续漫游和安全退出。
  • 世界系统中央林地、蘑菇坡、溪流、遗迹门、碰撞、检查点和可重建装饰。
  • 玩家系统键鼠与标准手柄、相机相对移动、冲刺、重置、互动和方向谜题。
  • 反馈系统卡通光照、Bloom、粒子、程序化音景、进度声效、减少动态和高对比。
  • 可靠性v2 进度快照、v1 迁移、最近有效备份、损坏隔离、恢复提示和单实例。
  • 交付工程Windows EXE、双语 NSIS、哈希清单、来源指纹、签名门禁和卸载验收。

产品版本 1.0

玩家看到的版本采用两段式 主版本.功能版本，当前正式从 1.0 开始。版本契约、 本地 pnpm 存储约束、WebView2 策略、依赖安全修复与统一教学档案都归入这一个 1.0 产品版本。

单一显示口径

Cargo、npm 与 Tauri 的机器清单必须满足各自的 SemVer 语法，构建脚本会机械补足所需格式， 但不会把它当成第二套产品版本。游戏、资料、发布清单、Windows 文件属性与“已安装的应用” 都只显示 version.json 中的 1.0。

02 · Architecture

总体架构：两个运行环境、三层规则

项目不是“Rust 把每一帧算好再交给网页”。正确分工是：Rust/Tauri 负责原生生命周期、持久状态、 确定性场景与低频边界；React/R3F 负责逐帧输入、运动、相机、呈现和界面。浏览器开发模式没有 Rust， 因而用 Web Worker 生成兼容场景，保持前端可以单独开发和测试。

玩家键鼠 / 手柄 / 指针
React界面、会话、状态编排
R3F / Three逐帧运动、相机、WebGL
Tauri IPC命令、事件、ACL
Rust生成、原生状态、存储
纯规则层游戏进度、方向谜题、输入归一化、运动与碰撞、选择 reducer。无 React、无 Three、无磁盘副作用。
适配层React hooks、GameplayController、PlayerController、treeApi、Worker client，把平台输入转换为纯规则动作。
呈现与副作用层R3F 场景、HUD、音频、Tauri 命令、持久化、文件导出、菜单、事件和安装器。

Tauri 桌面运行

pnpm tauri dev/build 创建原生窗口。Windows 内部由 Wry 驱动 WebView2； treeApi.ts 调用 Rust 命令并订阅事件。 场景数据由 Rust 生成，原生设置通过 Tauri Store 保存。

浏览器开发运行

pnpm dev 只启动 Vite。runtime.ts 判断没有 Tauri 后，让 fallback.worker.ts 在 Worker 中生成场景。它是开发容错路径，不是原生发布架构的替代。

核心不变量：相同 seed 的 Rust 生成必须确定；任何跨 IPC 的载荷必须经 Zod 校验； 渲染只能消费已提交的进度，不能自行发明“已经收集”或“已经净化”的状态；逐帧运动不经过 IPC。

03 · Monorepo

pnpm workspace 与 Cargo workspace 为什么共处一仓

这是一个双工作区单仓：JavaScript/TypeScript 由 pnpm 管理，Rust 由 Cargo 管理。根目录提供统一版本、 锁文件、质量命令和发布入口，使一次跨边界改动可以在同一个提交里验证全部消费者。

配置的单一真相源

  • tsconfig.base.json 集中严格类型选项，各 TS 包只补充自身环境。
  • biome.json 同时承担格式化和静态检查，避免 ESLint/Prettier 规则漂移。
  • vitest.config.ts 用 projects 模型发现应用与共享包测试。
  • Cargo.toml 统一 edition、技术版本、lints 与 release profile。
  • version.json 是产品版本与技术兼容版本的唯一映射。
  • pnpm-workspace.yaml 同时约束成员、依赖覆盖和本地缓存位置。

pnpm 数据绝不写到磁盘根目录

storeDir: .pnpm-store
cacheDir: .pnpm-cache
virtualStoreDir: node_modules/.pnpm
enableGlobalVirtualStore: false

内容寻址仓库位于 <repo>/.pnpm-store/，元数据缓存位于 <repo>/.pnpm-cache/，虚拟依赖树位于 <repo>/node_modules/.pnpm/。三者均被 Git 忽略， verify-pnpm-layout.ps1 会解析真实绝对路径， 拒绝盘符根目录、用户级全局虚拟仓库或越出项目的配置。

04 · End-to-end flow

沿一条真实请求读完整系统

下面以“玩家进入世界并接近一枚光种”为主线，把启动、设置、场景、逐帧运动、状态提交、保存和反馈串起来。

  1. 启动：main.tsx 创建 React 根节点，错误边界包围应用；特殊查询参数可进入本地 M2 证据工具。
  2. 水合：App.tsx 先读取本地进度，再向 Rust 请求设置；设置确认前不抢先加载错误 seed。
  3. 场景：treeApi.loadScene(seed) 在 Tauri 中 invoke('generate_tree')，在浏览器中调用 Worker。返回值先经 treeSceneSchema 验证。
  4. 呈现：SceneCanvas.tsx 把场景、世界、光照、粒子和后处理挂入 R3F Canvas。
  5. 输入：键盘、手柄被归一化为移动与动作意图；playerMotion.ts 根据相机水平前向、时间步和碰撞布局算新位置。
  6. 接近：GameplayController.tsx 只负责距离检测与输入适配，触发 reveal-seed 或 collect-seed 动作。
  7. 提交：reduceGameProgress 检查合法转换，返回不可变新快照；非法跳转直接保持原状态。
  8. 持久化：Zustand store 只在真实进度改变后写 v2 快照，写入前保留上一份有效快照作为备份。
  9. 反馈：R3F 根据已提交快照播放光种消散和树木复苏；AudioDirector 根据进度差异播放声效；QuestPanel 更新目标。
  10. 原生事件：Rust 周期性发出 magic-field，前端放进 ref，粒子在 useFrame 内读取，不让 React 每帧重渲染。
为什么强调“提交”：视觉动画可能被跳帧、卸载或减少动态设置缩短；如果动画本身决定进度， 存档与 UI 会失真。这里先由纯状态机完成原子转换，再让所有视觉与声音成为该事实的消费者。

05 · TypeScript + React 19

前端：用严格类型把框架留在边缘

TypeScript 不是给 JavaScript 加注释，而是让边界、状态转换和组件契约在编译期可证明。 React 则负责把这些数据映射为界面和生命周期；高频游戏数学留在纯函数与 R3F 帧循环中。

严格编译选项

strict、noUncheckedIndexedAccess、 exactOptionalPropertyTypes、noImplicitOverride 与 verbatimModuleSyntax 同时开启。数组索引因此是 T | undefined， 可选属性也不能用“显式 undefined”冒充缺失。

unknown 后再收窄

IPC、JSON 文件、本地存档和性能证据都是不可信数据。它们先保持 unknown， 再由 Zod 或专用解析器验证。禁止用 as SomeType 跳过边界检查。

可辨识联合

GameProgressAction、SelectionAction、Worker 协议和 SceneLoadResult 都用字面量字段区分分支。switch 让新增状态暴露未处理点。

标准装饰器

instrument.ts 的 @logged 和 @measure 使用 TC39 标准方法装饰器，为 IPC 加日志与计时， 不依赖旧式 experimentalDecorators。

React 的职责分层

入口main.tsx 只决定挂载哪个根应用，并安装 StrictMode 与错误边界。
编排App.tsx 管设置水合、场景加载、原生订阅、导出、菜单和跨系统回调。
状态state/store.ts 暴露选择器和动作，委托纯 reducer；组件不直接改内部对象。
适配Controller 组件把浏览器事件、手柄轮询、接近判定和 R3F ref 转换为领域动作。
呈现UI 与 Scene 组件根据 props/store 切片渲染，避免承担持久化或业务决策。

Hooks 在这里解决什么问题

  • useEffect 管理外部系统同步：IPC 请求、事件监听、键盘监听、设置持久化，而不是计算可派生值。
  • useRef 保存每帧读取的魔法场、场景命令 API、玩家位置与最新回调，更新它们不会触发 React 树重绘。
  • useMemo 缓存昂贵且纯的几何/实例矩阵；依赖必须真实完整，不能拿空数组“冻结”错误值。
  • useCallback 只在回调身份会影响订阅或子组件时使用；不把它当作无条件性能装饰。
  • StrictMode 会故意重复挂载 effect。asyncSubscriptionScope.ts 专门处理“监听 promise 尚未返回，组件已经卸载”的竞态。
错误边界的边界：React Error Boundary 捕获渲染和生命周期错误，但不会自动捕获事件处理器、 异步 promise 或 Rust 崩溃。后者必须在调用点处理，并由日志、错误状态或原生 panic hook 提供证据。

06 · State, save, input

状态、存档、输入与运动为何要分开

游戏最容易失控的地方，是把按键、位置、任务、动画和存档塞进同一个组件。 本项目把“瞬时输入”“逐帧运动”“持久进度”“界面会话”和“原生设置”拆成不同寿命的状态。

状态种类拥有者寿命与示例
输入意图playerInput.ts / Gamepad一帧或一次按下；移动向量、互动、冲刺、暂停。
运动状态PlayerController.tsx连续帧；位置、速度、朝向，由纯运动函数推进。
游戏进度gameProgress.ts + Zustand跨会话；光种、节点、树阶段、门、检查点、记忆。
会话 UIZustand当前运行；标题/游玩/暂停、覆盖层、选择、警告。
用户设置前端 store + Rust Store跨启动；主题、画质、音量、相机、无障碍。

进度状态机的不变量

light seed: hidden → revealed → collected
three collected: node dormant → ready
puzzle open: ready → cleansing
success: cleansing → restored + treeStage 1 + gateUnlocked
cancel/failure: cleansing → ready（不扣光种）

gameProgress.ts 用字面量联合、 Record<LightSeedId, LightSeedState> 和纯 reducer 表达这些规则。 解析旧存档时重新计算 collectedCount，并验证树阶段和门状态必须与净化状态一致； 这能拒绝“字段看似合法，但组合互相矛盾”的快照。

存档恢复策略

  1. 优先读取 dream-builder.progress.v2，通过完整不变量校验才接受。
  2. 主快照损坏时，把原始文本隔离到 corrupt key，再尝试最近一份有效 backup。
  3. 只有主快照不存在时才迁移 v1；迁移补上检查点与记忆字段，不迁移中途 cleansing 状态。
  4. 正常写入前先把上一份有效主快照变成 backup；“开始新旅程”则原子替换并清理旧备份。
  5. Storage 不可用或写失败时保持当前会话可玩，并通过 UI 提示，不能静默假装已经保存。

运动与碰撞

playerInput.ts 把 WASD、方向键和手柄轴统一成 归一化意图；playerMotion.ts 将它转换到相机水平坐标系， 按加速/减速和最大步长推进。世界边界、圆形障碍与矩形障碍来自 forestLayout.ts，同一份布局同时被碰撞和呈现消费， 避免“看见的墙”和“撞到的墙”漂移。

为什么不用物理引擎

当前只有平面行走、静态障碍和显式边界。纯数学碰撞更小、更确定、更易测；出现斜坡、动态刚体或大量碰撞前，引入物理引擎只会增加同步成本。

为什么相机不进 Rust

相机和玩家运动每帧更新，把它们经 IPC 往返会增加延迟与序列化负担。Rust 负责低频、可持久、可重放的数据，帧循环留在 WebView。

07 · Realtime graphics and audio

3D 世界：React 声明场景，Three 执行渲染

react-three-fiber（R3F）不是另一套 3D 引擎；它是 Three.js 的 React renderer。 JSX 描述场景图，R3F 把 <mesh>、材质、光源和相机映射为 Three 对象， 最终仍由 WebGL 在 WebView2 中绘制。

Canvas

SceneCanvas 配置相机、DPR、色调映射、场景 API、后处理和截图所需的 drawing buffer。

世界

GameplayWorld 组合玩家、卡通森林、光种、记忆、检查点和净化节点。

智慧树

TreeContent 把 Rust 返回的枝干、叶簇、符文、水晶与地面光环组合为场景。

程序化森林

CartoonForest 按 seed 和质量档生成可重建装饰，但关键路径与碰撞保持稳定。

粒子

MagicParticles 用 BufferGeometry 和 useFrame 更新位置，从 ref 读取后端场。

后处理

Bloom 只服务发光物体；画质档与减少动态控制成本和强度，不能让装饰破坏目标可读性。

关键图形概念

实例化与 draw call

每棵草、每片叶都单独 mesh 会产生大量 draw call。叶簇等重复物体使用 InstancedMesh：共享几何和材质，只为每个实例提供变换矩阵。它牺牲部分逐对象自由， 换来显著减少 CPU 提交开销。

材质、色调映射与 Bloom

PBR 材质根据光照计算表面；emissive 让对象自身发亮；ACES 色调映射把 HDR 亮度压回屏幕范围； Bloom 再把超过阈值的亮部扩散。三者顺序和曝光共同决定“发光”是否通透而不糊成一片。

GLSL 水晶与 Fresnel

crystalMaterial.ts 在顶点阶段传递视图法线和视线方向，在片元阶段以 pow(1 - dot(normal, viewDir), power) 形成掠射角更亮的 Fresnel 边缘， 再用时间 uniform 制作流光。hover 与选中只调 uniform，不重建材质。

第三人称相机

PlayerController 维护玩家后上方偏移，把相机和 target 随玩家位移一起平移；移动方向只取相机 水平前向，俯视不会让角色钻入地面。减少动态模式降低相机滞后和强反馈，保证舒适性。

液态玻璃 UI

GlassProvider 统一主题和质量， liquid-glass.css 用半透明 tint、 backdrop-filter、边缘高光和阴影建立层次。浏览器不支持模糊、系统要求减少动态或设备能力较弱时， 会退化到稳定不透明面板；视觉效果不能成为可读性的前置条件。

程序化音频

forestAudio.ts 使用 Web Audio API 合成环境层， progressAudio.ts 将进度差异映射为短声效。 AudioDirector 在首次用户手势后安全恢复 AudioContext，分别应用主音量、环境音和效果音；静音与页面卸载必须释放节点， 避免后台声音和资源泄漏。

08 · Accessibility and input devices

无障碍不是附加皮肤，输入设备也不只有键盘

单机离线游戏同样要面对“看不清、不能久盯动画、只用键盘、只用手柄”的玩家。 本项目把无障碍表达成受校验的设置项、根节点状态类和可测试的输入适配层， 而不是散落在各个组件里的临时判断。

设置类型与范围它真正改变什么
reducedMotion布尔降低相机滞后、粒子幅度与强闪反馈，但保留状态可读性
highContrast布尔根节点加 app-root--high-contrast，提高玻璃面板与次要文本对比
textScalenormal / large根节点加 app-root--large-text，放大 HUD 与覆盖层字号
showHints布尔控制新手提示是否出现，让熟练玩家清空界面
cameraSensitivity整数 50–150缩放相机响应，照顾晕动敏感与精细操作
masterVolume 等整数 0–100主/环境/效果三条独立音量，可完全静音仍可通关

这些字段和 seed、theme 在 同一个 settingsSchema 中定义并带默认值， 因此“无障碍设置”与其他设置走完全相同的校验、IPC 与持久化路径：Rust 侧先验证范围， 再写入 Tauri Store；前端 App.tsx 只把已提交的切片映射为根节点类名。 旧存档缺字段时由 schema 默认值补齐，不会让界面进入半初始化状态。

系统偏好与游戏内设置并存： styles.css 同时响应 @media (prefers-reduced-motion: reduce)。操作系统已经声明“减少动态”时不需要玩家再找一次开关， 而游戏内开关又允许在系统未声明时单独降低动效。两者是“或”的关系，不是互相覆盖。

三种输入设备，两种事件模型

键盘：事件驱动

useKeyboardShortcuts 只在 window 上绑定一次监听，处理函数存在 ref 中，因此既没有陈旧闭包，也不会每次渲染都重新订阅。

指针：事件驱动

useInteractive 把 R3F 的 pointer 事件转成选择 reducer 的动作，悬停与选中仍是纯状态转换。

手柄：轮询驱动

Gamepad API 不提供按钮/摇杆事件，只能读取快照。 GamepadNavigator 在 requestAnimationFrame 中采样，并与上一帧比较做边沿检测。

差异被限制在适配层：三类设备最终都产生同一套意图（移动向量、互动、冲刺、暂停、方向）， 由 playerInput.ts 归一化后交给纯逻辑。 边沿检测尤其重要——长按手柄按键在每一帧都是“按下”，若不比较上一帧状态，一次按压会被当成上百次暂停切换。

模态焦点：Tab 不能逃出对话框

  • useModalFocus 打开时聚焦首个控件，关闭时把焦点还给触发它的控件。
  • Tab / Shift+Tab 在对话框内循环，键盘用户不会“掉”到被遮挡的 HUD 上。
  • Esc 与 ? 优先交给当前对话框，而不是全局游戏快捷键。
  • 全局快捷键遇到 [aria-modal="true"]、输入框或可编辑元素时主动让路，避免“打字触发截图”。
  • 手柄在净化谜题里被映射为方向键，在其他对话框里被映射为焦点漫游，两种含义不会互相污染。
自动化能证明什么：组件测试用角色、可访问名称和焦点顺序断言标题、设置、帮助与覆盖层， 快捷键与 手柄采样也有确定性测试。 但屏幕阅读器实机朗读、实体手柄完整听测与真人操作舒适度仍是外部门槛，不能由 jsdom 断言代替。

09 · Performance evidence

性能不是一个 FPS 数字，而是一条可复核证据链

场景必须在真实 Tauri/WebView2 目标设备上持续运行，才能代表交付体验。项目内置记录器只保存有界聚合， 同时避免收集玩家路径或逐帧行为数据。

  • PerformanceProbe 在帧循环读取帧间隔与 Three renderer 统计。
  • PerformanceMetricsRecorder 用固定 0.5ms 直方图估计分位数，不保留无限增长的原始帧数组。
  • 状态 marker 最多 128 个、phase 最多 32 个；名称与环境字符串有长度上限，导入报告也重新校验。
  • 报告给出平均 FPS、1% low 等价值、P50/P95/P99、最长帧、慢帧比例、draw calls、三角形和可用堆峰值。
  • scene-load 与 cleansing 单独分段，不能用稳态平均值掩盖加载或净化尖峰。
  • 浏览器主循环只能观察 CPU/呈现间隔，不能直接得到 GPU frame time；需要 GPU 指标时另用目标设备分析器。

已归档事实

目标 Windows 设备已有十分钟原生性能报告，覆盖场景加载与净化，并通过当前 M2 帧率预算。

仍未替代的事实

真实性能通过不代表五位新玩家能理解目标；自动化和证据工作台都不能代替真人无提示观察。

10 · IPC contract

IPC：跨语言边界必须同时有静态类型和运行时证据

TypeScript 类型在运行时会被擦除，Rust 类型也不会自动保护已经变成 JSON 的数据。 因此 IPC 的正确模型是：Rust 按 serde 合约序列化，前端先把载荷视为 unknown， 经 Zod 成功解析后才进入应用核心。

React 调用treeApi 方法
Tauri invoke命令名 + 参数

serde JSONcamelCase wire

当前命令面

命令责任失败语义
generate_tree设置活动 seed、记录历史、命中缓存或确定性生成场景Result<TreeScene, AppError>
detail_info按场景对象 id 返回符文/水晶/叶簇说明未知 id 是结构化错误

事件与请求的区别

命令是请求/响应，适合“给我一个场景”“保存这份设置”；事件是后端主动推送，适合周期魔法场和原生菜单。 events.rs 发出 magic-field， menu.rs 把菜单 id 转成 menu:<id>。 每个前端事件 payload 仍要校验；事件并不因为来自本进程就自动可信。

修改 wire 格式时的四方同步

  1. Rust domain struct 与 serde rename/enum 表示；
  2. packages/ipc-contracts 的 Zod schema 和推导类型；
  3. 浏览器 Worker 回退生成器与协议；
  4. Rust 序列化集成测试、Zod 契约测试和前端消费者测试。
常见错误：只改 TS interface 不会改变运行时校验；只改 Rust 字段会让旧前端回退； 用 as TreeScene 会把协议错误推迟到渲染深处，变成更难诊断的 WebGL 故障。

11 · Rust backend

Rust 后端：领域模型、确定性生成与原生副作用

Rust 部分同时是库和可执行程序。main.rs 保持极薄，只调用库的 run()； 可测试逻辑放在 domain、generation、magic 和 state 中，Tauri 命令只做边界适配。

domain/Vec3、Seed、Energy、树场景、细节、魔法场和 builder；只表达数据与不变量。
generation/RNG trait、SeededRng、SceneGenerator trait 与 FantasyTreeGenerator；给定 seed 可重放。
state.rs设置、seed 历史、活动 seed 与场景缓存，封装在 Arc<Mutex<Inner>>。
commands.rs七个薄 IPC 命令；输入校验、状态访问、异步导出与结构化错误。
lib.rs插件、菜单、setup、托管状态、后台事件、命令注册和进程生命周期。

所有权与借用

只读取 id 的函数接收 &str，生成器借用 &mut impl Rng； 只有返回或跨线程/状态边界时才拥有并克隆数据。克隆不是“让借用检查器安静”的默认工具。

Newtype 与不变量

Seed(u64) 防止任意数字混用；Energy(f32) 只能通过夹紧构造， 因而任何已存在的 Energy 都落在 0..1。serde transparent 保持 wire 仍是数字。

Trait 与泛型接缝

Rng 只要求实现 next_u32，默认方法派生浮点与范围； SceneGenerator 定义生成与细节查询，使调用方依赖能力而不是具体算法。

Builder 与枚举

TreeSceneBuilder 用移动 self 的链式 API 组装结果；DetailKind 与 AppError 用穷尽 match，让新增变体在遗漏处理处产生编译错误。

错误处理

AppError 由 thiserror 派生错误文本， 并手写 Serialize 稳定输出 { code, message }。可预期失败返回 Result 并用 ? 传播；panic 只代表不变量或启动级错误。panic hook 会把崩溃写入日志， 但绝不能把秘密或用户数据塞进错误文本。

共享状态与异步纪律

AppState 克隆的是 Arc，不是复制状态。 每个方法内部短暂加锁，复制所需值后立即释放。事件任务 在 interval.tick().await 之后才读取设置，绝不让同步 Mutex guard 跨越 await。 文件导出使用 tokio::fs::write，避免阻塞异步执行器线程。

确定性生成

SeededRng 的输出只由 seed 与调用序列决定；FantasyTreeGenerator 依序生成树干、树冠、符文和水晶， 细节 id 也稳定。确定性让缓存、导出、故障复现、测试和跨会话重建成立。任何“为了视觉随机”而读取系统时间或 平台随机源都会破坏这条合同；需要会话变化时，应显式引入独立 seed 并把它纳入存档。

12 · Tauri 2

Tauri：原生外壳不是一个打包按钮

Tauri 把系统 WebView、Rust 进程、窗口、菜单、托盘、插件和权限系统装配成一个桌面应用。 它的核心价值不是“把网站变 EXE”，而是以明确授权的 IPC 把 Web UI 与原生能力连接起来。

Builder 启动顺序

  1. 安装 panic logger，使未捕获 Rust panic 进入诊断日志；
  2. 安装 single-instance，第二次启动时聚焦主窗口；
  3. 安装 log、store、dialog 和 opener 四个插件——注意这里没有文件系统插件，导出写盘由 Rust 命令自己完成；
  4. 构建原生菜单并把点击转发为前端事件；
  5. 在 setup 中载入设置、创建 AppState、注册托盘并启动魔法场任务；
  6. 通过 generate_handler! 注册命令；
  7. generate_context!() 嵌入编译期配置并进入事件循环。

托管状态 State<'_, AppState>

app.manage(state) 把一个线程安全值交给 Tauri 容器。命令形参中的 State 是带生命周期的借用句柄，命令不能把它任意保存到全局。AppState 内部再用 Arc/Mutex 管理共享所有权与可变性。

插件与动态导入

Rust 插件提供原生实现，前端对应 JS 包提供类型安全调用。保存对话框、路径和 opener 只在 Tauri 分支动态导入， 既避免浏览器开发模式执行原生 API，也把可选代码移出首屏 bundle。插件装上并不等于前端自动有权限，仍需 capability 授权。

窗口、菜单与单实例

tauri.conf.json 定义主窗口尺寸、最小尺寸、背景色、居中和 Win11 Mica； 不支持 Mica 的系统会优雅忽略。原生菜单和托盘使用稳定 id，前端统一处理动作。二次启动不会创建第二个世界实例， 而是显示、取消最小化并聚焦现有窗口，避免并发写存档。

Tauri 路径基准的容易混淆点

before*Command

运行 cwd 是包含 Tauri 配置目录的父目录，即 crates/，所以使用 pnpm -C .. dev/build 才回到仓库根。

frontendDist

它相对配置文件 crates/dream-builder/tauri.conf.json，所以是 ../../apps/desktop/dist。两者不是同一个基准。

13 · Windows WebView runtime

WebView2：使用 Evergreen，不固定运行时版本

Windows 打包版的前端确实运行在 Microsoft Edge WebView2 Runtime 中，但 React 代码没有直接创建或调用 CoreWebView2。调用链由 Tauri → tauri-runtime-wry → Wry → WebView2 COM 完成；前端面对的是标准 Web API 和 Tauri API，而不是某个特定版本的 WebView2 SDK 对象。

结论：不锁定 WebView2 Runtime 版本是本项目正确的默认策略。Evergreen Runtime 由 Windows/ Microsoft Edge Update 维护，各用户在某一时刻的补丁版本可能不同，因此无法也不应要求“所有机器严格同一 WebView2 版本”。 应统一的是受支持行为、Web 标准与回归测试，不是运行时补丁号。

当前配置到底做了什么

"webviewInstallMode": {
  "type": "downloadBootstrapper",
  "silent": true
}

这是 Tauri 的 Evergreen 引导安装模式：安装器检查运行时，缺失时由 Microsoft bootstrapper 获取合适的 Evergreen Runtime； 已安装时应用直接使用系统运行时。配置没有 fixedRuntime 路径，也没有版本字段。 verify-version-contract.ps1 会阻止误改成固定运行时。

方案优点代价本项目
Evergreen bootstrapper体积小、持续安全更新、Windows 10/11 普遍可用用户补丁版本不同；首次缺失时需要获取运行时采用
Offline installer安装时不依赖网络，仍安装 Evergreen安装包更大；需要随包维护引导文件仅离线部署需求明确时评估
Fixed Version每台机器使用完全相同引擎约增加约 180MB、应用自行承担安全更新与兼容维护不采用

开发浏览器与发布 WebView 的差异

  • pnpm dev 只是 Vite 服务器；你用 Chrome 打开就是 Chrome，用 Edge 打开就是 Edge，不自动变成 WebView2。
  • pnpm tauri dev 和安装后的 EXE 才由 Tauri 创建 WebView2 原生窗口，并启用 IPC、菜单和插件。
  • 因此必须同时做浏览器快速测试和真实 Tauri 冒烟；只在 Chrome 通过不能证明 WebView2 原生集成通过。
  • WebView2 与 Edge 共用 Chromium/平台技术，但 Runtime 是面向嵌入式应用的独立安装与更新通道。

怎样验证而不错误锁版本

  1. 静态验证配置是 downloadBootstrapper 且不存在 fixed path；
  2. 在支持的最低/当前 Windows 环境安装并首次启动；
  3. 确认 msedgewebview2.exe 子进程、原生 IPC、WebGL、音频与导出工作；
  4. 记录测试时的 Windows 与 Runtime 版本用于复现，但不要把该值写成应用启动的硬性等号；
  5. WebView2 大版本变化后用 CI、目标机和干净账户回归关键流程。

延伸阅读： Tauri Windows installer、 Microsoft Evergreen 与 Fixed Version。

14 · Security boundaries

桌面应用仍然有浏览器边界、文件边界与供应链边界

“离线单机”不等于没有攻击面。WebView 内容、IPC 参数、本地 JSON、文件路径、插件权限、依赖安装和发布产物都需要明确边界。

Capability / ACL

default.json 只授权 main 窗口需要的 core 关闭窗口、保存对话框、导出文件定位，以及限定在 $APPLOG 下的日志目录打开能力。 存档与日志插件只由 Rust 后端使用，不向 WebView 暴露；未使用的直接文件系统插件已经移除。

CSP

配置限制默认资源、图片、样式、字体和连接来源，只开放 Tauri IPC 所需 scheme。 unsafe-inline 目前只用于样式；脚本没有放开远程源或 inline 执行。

边界校验

Rust 设置先验证范围；前端 IPC 与证据导入按 schema；存档验证跨字段一致性；性能文本有长度上限。

隐私最小化

性能记录不保留逐帧路径，M2 工具只用 P01–P05 匿名编号，不联网、不自动上传、不采姓名账号。

pnpm desktop:verify-security 会拒绝远程开发源、CSP 通配符或 unsafe-eval、多余 capability、越界路径以及重新注册直接文件系统插件；它也是 pnpm check 的固定阶段。

文件导出的信任边界

路径来自用户主动保存对话框，Rust 负责实际写入。错误需要带操作上下文，但不能回显秘密内容。 应用不递归扫描用户磁盘，也不在后台删除目录。发布脚本只操作经过解析、位于项目 output 或系统临时根下的明确路径。

依赖与构建供应链

  • pnpm 与 Cargo 锁文件提交入库，CI 使用 frozen/locked 模式。
  • pnpm audit 检查 JavaScript 公告；高风险传递依赖通过精确 override 修补，并重新生成锁文件。
  • 只允许必要的包安装脚本（Biome 与 esbuild），减少任意生命周期脚本执行面。
  • 代码签名证书只从当前用户证书库按指纹读取；PFX、密码和私钥绝不进入仓库或日志。
  • 候选包与生产包在清单中明确区分；未签名文件不能因为哈希正确就宣称生产发布。

15 · Build toolchain

两套构建系统：Vite 负责网页产物，Cargo 负责原生产物

“能跑起来”和“能交付”之间隔着构建配置。前端由 Vite 在开发期用 esbuild 转换、在发布期用 Rollup 分块； Rust 侧由 Cargo 与 build.rs 生成可执行文件并改写 Windows 版本资源。 两条链路都必须可重复、可验证，并且不能悄悄改变玩家看到的版本。

开发期：Vite dev server

  • 源码以原生 ES module 直接提供，只按需转换，因此冷启动与热更新不随项目规模线性变差。
  • server.strictPort 固定 127.0.0.1:1420：Tauri 配置按此端口连接，端口被占用时应当失败而不是悄悄换端口。
  • clearScreen: false 保留 Tauri CLI 的原生日志，否则 Rust 编译输出会被前端刷屏覆盖。
  • envPrefix: ['VITE_', 'TAURI_'] 让 Tauri 注入的环境变量可以进入前端，同时仍然拒绝暴露任意进程变量。
为什么显式设置 esbuild.target: 'es2022'： Vite 开发期默认按接近 esnext 提供源码，而 Chromium 尚不能解析 TC39 标准装饰器语法。 instrument.ts 的 @logged / @measure 因此会在浏览器开发模式直接语法报错。把 target 对齐到 TypeScript 的 ES2022， 使开发与生产使用同一套降级规则；viteDevTransform.test.ts 把这条结论固化成回归测试，避免配置被“顺手清理”掉。

发布期：Rollup 分块与预算

R3F 的 Canvas 会注册完整 Three 命名空间，如果和应用代码打进同一个文件， 每次业务改动都会让用户重新下载整个 3D 引擎。 viteChunks.ts 因此把依赖按稳定度切成三块：

react-three-runtimefiber、drei、three-stdlib、maath250,000
three-effectspostprocessing 与 Bloom 通道120,000
SceneCanvas按需加载的场景入口100,000
GLTFExporter只有导出时才需要的序列化器80,000
  • onlyExplicitManualChunks 阻止 Rollup 把共享的 React 依赖卷进延迟加载的场景块。
  • verify-desktop-bundle.ps1 在每次 pnpm build 后运行：每个前缀必须恰好一个 chunk、逐块不超预算、除引擎外没有超过 500,000 字节的块。
  • 它还检查 index.html 不能直接引用这些延迟 chunk——否则“代码分割”只是把一个大文件拆成几个同时下载的文件。
  • 预算是硬失败而不是警告：chunkSizeWarningLimit 只影响提示，真正的门禁在脚本里。

原生期：build.rs 与 Windows 版本资源

build.rs 是 Cargo 在编译 crate 之前运行的构建脚本。它做两件事： 先由 tauri_build 嵌入配置并生成 Windows 资源文件，再在 Windows 目标上把资源里的 FileVersion 与 ProductVersion 改写成 version.json 中的两段式公开版本，最后用 embed_resource 重新编译资源。

  • cargo:rerun-if-changed 指向 version.json，改版本号会触发重新构建而不是复用旧资源。
  • 脚本先校验 productVersion 恰好两段、全为数字、无前导零，非法值直接让构建失败。
  • 替换时统计命中次数，不等于一次就 panic。宁可构建失败，也不要产出“版本字符串只改了一半”的 EXE。
  • 这解释了为什么 Cargo 清单里的三段式兼容值不会出现在文件属性里：它在链接前就被替换掉了。

release profile 统一在根 Cargo.toml：lto 做跨 crate 内联， codegen-units = 1 牺牲编译并行度换取更好的优化，strip 去掉符号表以缩小体积。 这些只应用于发布构建，调试构建保持快速与可调试。

统一入口：justfile 是跨语言任务入口， just check / just bundle 包住 pnpm 与 cargo 两侧命令； 根 package.json 的脚本与之一一对应，因此本机、CI 和发布使用的是同一组命令， 而不是三份互相漂移的说明。

16 · Versioning and dependencies

用一个两段式产品版本控制全部展示

用户要求的版本语义由两段数字表达，底层工具的格式要求则由机械兼容层承担。两者必须从一个文件派生并自动对照， 不能靠开发者手工记忆在多个清单中同步。

位置当前值原因
游戏 UI / 文档 / Changelog1.0唯一的产品版本
发布目录与交付文件名output/release/1.0面向玩家和发布人员
release manifestversion: 1.0不再暴露第二个版本字段
package.json / Cargo / Tauri构建兼容值（不展示）只满足工具解析要求
Windows EXE / 已安装的应用1.0安装器、主程序、卸载器与 DisplayVersion 一致

升级规则

  • 小的新功能：只增加第二段，不对玩家暴露额外补丁位。
  • 非常大的功能模块：增加第一段并把第二段归零。
  • 修复与内部重构：在同一候选内重新构建时用来源提交与哈希区分，不制造第二套产品版本。
  • 历史证据：原始测量 JSON 保持不可改写；当前产品资料只引用两段式版本。

依赖版本与产品版本不是一回事

React、Tauri、pnpm、WebView2 等依赖各自使用自己的版本政策；产品版本 1.0 不要求依赖采用相同数字。 依赖升级必须看 API、锁文件、公告、目标平台与实际回归。当前依赖解析还通过 override 固定 postcss 8.5.23 和 nanoid 3.3.17，用于消除已知安全公告；这类覆盖要在上游链路自然升级后再审慎移除。

17 · Quality gates

“没有 LSP 告警”要落到可重复的编译与静态门禁

编辑器的 LSP 诊断依赖本机插件与当前打开文件，不能作为唯一交付证据。项目把同类检查固化为命令： TypeScript 编译器、Biome、Vitest、Vite、Rustfmt、Clippy、Cargo tests 与原生打包共同构成新鲜证据。 

pnpm check
cargo fmt --check
cargo test --workspace --locked
cargo clippy --workspace --all-targets --locked -- -D warnings
cargo check --workspace --all-targets --locked

pnpm check 内部顺序

九个阶段按“最便宜、最容易出错的先跑”排列：契约类检查在几秒内失败，编译与测试放在后面， 最慢的生产构建放在最后。任何一步非零退出都会中断整条链。

  1. version:verify：两段式产品版本与各机器清单的兼容值映射、NSIS 显示版本、WebView2 Evergreen 配置，并扫描公开资料是否泄漏了第二套版本；
  2. desktop:verify-security：CSP 不含通配符或 unsafe-eval、capability 保持最小、路径不越界、未重新引入直接文件系统插件；
  3. docs:verify：教学档案的 HTML 结构、必需主题、章节可达性、重复 id、锚点、本地链接与同级文档入口；
  4. pnpm:verify-layout：store/cache/virtual store 解析后的绝对路径都在项目根内；
  5. m2:verify：归档的原生性能报告哈希、来源与帧率预算未被改写；
  6. biome check：格式、可疑代码和导入组织；
  7. tsc --noEmit：所有工作区包严格类型检查；
  8. vitest run：纯规则、契约、组件、存档、性能与开发变换测试；
  9. vite build：TypeScript 编译、生产分块，以及 verify-desktop-bundle.ps1 的 chunk 预算。

纯单元测试

状态机、碰撞、方向谜题、输入、音频差异、统计直方图和 schema 可在 Node/jsdom 中快速确定地运行。

组件测试

Testing Library 从角色、标签和用户行为断言标题、设置、帮助、覆盖层与证据工具，不依赖私有实现。

跨边界测试

Rust 集成测试验证 camelCase 序列化和引用完整性；Vite transform 测试防止浏览器开发模式装饰器语法回归。

真实运行

浏览器冒烟验证 WebGL/UI，Tauri 冒烟验证 WebView2、IPC、菜单、单实例、日志和退出，安装生命周期验证 Windows 集成。

测试设计纪律

  • 测试外部行为和不变量，不锁死组件内部变量或随机实现细节。
  • 用注入时钟、确定 seed 和显式事件代替不受控等待；性能记录器的自动停止也要可控测试。
  • 不通过删除断言、跳过测试或扩大阈值来“修复”失败；先确定产品合同是否真的改变。
  • 打包成功不等于安装成功，安装成功不等于首次启动成功，首次启动成功不等于真人可玩性通过。

18 · Continuous integration

CI 的价值在于“别人的机器也能重现”，不在于绿色徽章

本机门禁证明的是“在我的机器上、用我此刻的缓存通过了”。持续集成把同一组命令搬到一台干净的 Windows runner 上执行，用来暴露未提交文件、锁文件漂移、平台假设和只在本地存在的工具。

工作流触发做什么
ci.yml每次 push 与 pull request两个并行 job：TypeScript/React 跑 pnpm check，Rust/Tauri 跑 fmt、test 与 Clippy
release.yml手动触发或 v* 标签跑完整发布门禁并上传带校验和的未签名 Windows 候选包

几个配置为什么是这样写的

  • runs-on: windows-latest：Windows 是唯一受支持的目标。门禁脚本是 PowerShell，NSIS、WebView2 与文件属性也都只有在 Windows 上才有意义，在 Linux runner 上“通过”不构成证据。
  • permissions: contents: read：显式收窄 GITHUB_TOKEN。构建与测试不需要写仓库，最小权限让被攻破的依赖也无法推送提交。
  • concurrency + cancel-in-progress：同一分支的新推送取消旧运行，既省算力也避免用过期结果判断当前代码。
  • node-version-file: .nvmrc：Node 版本从仓库文件读取，而不是写死在工作流里，本机与 CI 只有一个真相源。
  • pnpm/action-setup：不指定版本，改为读取 package.json 的 packageManager 字段，因此 CI 用的就是本地那一版 pnpm。
  • --frozen-lockfile：锁文件与清单不一致时安装必须失败。CI 的职责是复现既定依赖树，不是替开发者解析新版本。
  • if-no-files-found: error：产物目录为空时上传步骤失败。否则一次“成功但没有产物”的运行会被误当成发布成功。
两个 job 为什么不合并：前端与 Rust 没有先后依赖，拆开可以并行， 并且失败时一眼看出是哪一侧回归。Rust job 不安装 Node，前端 job 不安装 Rust 组件， 各自的环境也因此更小、更快、更少偶发失败。

CI 通过之后仍然没有被证明的事

  • CI 不启动 WebView2 原生外壳，不能替代 pnpm tauri dev 与安装版冒烟。
  • CI 产出的候选包是未签名的；受信任代码签名依赖当前用户证书库，无法也不应放进公共 runner。
  • CI 不做干净账户的安装—升级—卸载生命周期验证，也没有实体手柄和音频输出设备。
  • CI 永远不能替代五名首次接触玩家的无提示观察。

换句话说，绿色 CI 是“候选包可以进入人工验收”的前提，而不是“可以发布”的结论。 人工门槛的当前状态见 docs/game/README.md。

候选包的六个文件

  • Dream-Builder-Fantasy-Tree_1.0_x64.exe：便携入口；
  • Dream-Builder-Fantasy-Tree_1.0_x64-setup.exe：推荐 NSIS 安装器；
  • LICENSE.txt 与 README-zh-CN.md；
  • SHA256SUMS.txt：四个交付载荷的摘要；
  • release-manifest.json：schema 5、唯一产品版本、来源提交、源码树指纹、文件和签名状态。

源码指纹为何不只看 Git commit

本地候选可能在 dirty worktree 构建；只记 HEAD 会把多个不同源码状态写成同一身份。脚本枚举受 Git 管理和未忽略文件， 对路径、大小与 SHA-256 形成排序索引，再计算整棵源码树指纹。产物生成后任何源文件变化都会让独立验证拒绝旧清单。

候选、生产和签名

类型允许状态可以怎样称呼
本地候选显式允许 dirty；EXE 必须明确 NotSigned；清单记录 sourceDirty开发候选，不得公开宣称正式版
干净候选干净提交、全部门禁、未签名可复核发行候选，仍非生产分发
生产包干净源码、证书库有效代码签名、时间戳、两份 EXE 均 Valid满足其余人工门槛后才可正式发布

安装与卸载合同

release-install-state.ps1 在安装后检查唯一卸载项、 两段式版本 1.0、安装目录、主 EXE 和快捷方式；卸载后要求卸载项、程序目录、快捷方式和进程全部消失。 玩家数据可按升级/诊断政策保留，脚本只报告其存在，不读取或删除。完整手册见 release-runbook.md。

21 · Guided learning

建议的七段学习路线

  1. 先运行浏览器版：pnpm dev，完成标题到净化，观察没有 Rust 时的回退警告。
  2. 读纯规则：从 gameProgress、purificationPuzzle、playerInput、playerMotion 的测试开始，理解确定状态转换。
  3. 接上 React：追踪 store → GameplayController → UI/Scene，观察组件怎样消费同一快照。
  4. 进入 3D：从 SceneCanvas 到 GameplayWorld，再拆解 TreeContent、CartoonForest、实例化、shader 和性能探针。
  5. 练习无障碍：只用键盘走一遍标题—设置—帮助—净化，再打开系统“减少动态”对比表现差异。
  6. 跨过 IPC：比较 Zod schema 与 Rust serde struct，跟踪 generate_tree 请求和 magic-field 事件。
  7. 运行原生与发布：pnpm tauri dev 验证 WebView2/IPC，再阅读 capability、CSP、构建分块、CI 工作流、发布清单和安装状态脚本。
一次安全练习：给 IPC 场景增加一个可选、向后兼容字段。先写 Rust/TS 两侧失败测试， 再同步 domain、serde、Zod、Worker 和消费者，最后运行全部门禁。这个练习会触及本项目最重要的架构边界。

22 · Glossary

术语速查

Tauri以系统 WebView 呈现前端、以 Rust 提供原生能力和安全 IPC 的桌面框架。
WebView2Microsoft Edge Chromium 的 Windows 嵌入式运行时；本项目采用 Evergreen 自动维护模式。
WryTauri 运行时使用的跨平台 WebView 抽象，在 Windows 下连接 WebView2。
IPC进程/运行时边界通信；这里包括前端 invoke Rust 命令和 Rust emit 前端事件。
CapabilityTauri 2 的窗口级权限清单，决定前端可调用哪些 core/plugin 能力。
CSP内容安全策略，限制 WebView 可加载和连接的资源来源。
R3Freact-three-fiber，Three.js 的 React renderer，用 JSX 声明场景图。
Draw callCPU 向 GPU 提交一次绘制；大量小 mesh 会使其升高，实例化可合并重复绘制。
Fresnel视线接近表面掠射角时反射更强的现象，常用于水晶、玻璃和边缘光。
InstancedMesh共享几何与材质、只为每个实例提供变换矩阵的 Three 对象，用于压缩重复物体的 draw call。
Vite前端构建工具：开发期用 esbuild 按需转换并提供原生 ESM，发布期交给 Rollup 打包。
esbuildGo 编写的极快转换器；本项目用它把 TypeScript 与标准装饰器降级到 ES2022。
RollupVite 生产构建使用的打包器；manualChunks 在这里把 Three 引擎切成独立可缓存块。
代码分割把产物拆成按需加载的块。只有在入口不提前引用这些块时，它才真正减少首屏成本。
build.rsCargo 在编译 crate 前运行的构建脚本；这里用于嵌入 Tauri 配置并改写 Windows 版本资源。
GitHub Actions仓库内声明的 CI 服务；本项目在 Windows runner 上运行与本机相同的门禁命令。
Frozen lockfile锁文件与清单不一致时直接失败的安装模式，保证 CI 复现既定依赖树而不是解析新版本。
焦点陷阱让 Tab 在模态对话框内循环并在关闭时归还焦点的可访问性模式。
边沿检测比较相邻两次采样只在状态跳变时触发动作；轮询式 Gamepad API 必须这样处理长按。
prefers-reduced-motion操作系统级“减少动态”偏好的 CSS 媒体查询；与游戏内开关是“或”的关系。
Zustand轻量 React 状态库；本项目用选择器订阅切片，核心转换仍由纯 reducer 决定。
Zod运行时 schema 库，可在解析成功后推导 TypeScript 类型。
Newtype用单字段 Rust 类型给裸值增加领域语义与构造不变量。
Arc<Mutex<T>>原子引用计数提供跨所有者共享，Mutex 提供互斥可变访问；不能跨 await 持有同步锁。
确定性相同输入始终得到相同输出，是缓存、复现、测试和程序化存档重建的基础。
NSISWindows 安装器系统；本项目只生成一个当前用户、简中/英文安装包目标。
AuthenticodeWindows 可执行文件代码签名体系；有效受信任签名是生产分发门槛。
1% Low最慢约 1% 帧的等效 FPS，用于暴露平均 FPS 隐藏的卡顿。
