Build toolchain

两套构建系统：Vite 负责网页产物，Cargo 负责原生产物

“能跑起来”和“能交付”之间隔着构建配置。前端由 Vite 在开发期用 esbuild 转换、在发布期用 Rollup 分块； Rust 侧由 Cargo 与 build.rs 生成可执行文件并改写 Windows 版本资源。 两条链路都必须可重复、可验证，并且不能悄悄改变玩家看到的版本。

开发期：Vite dev server

  • 源码以原生 ES module 直接提供，只按需转换；通常能减少开发期等待，但实际启动成本仍取决于模块数量和依赖预构建。
  • server.strictPort 固定 127.0.0.1:1420：Tauri 配置按此端口连接，端口被占用时应当失败而不是悄悄换端口。
  • clearScreen: false 保留 Tauri CLI 的原生日志，否则 Rust 编译输出会被前端刷屏覆盖。
  • envPrefix: ['VITE_', 'TAURI_'] 让 Tauri 注入的环境变量可以进入前端，同时仍然拒绝暴露任意进程变量。
为什么显式设置 esbuild.target: 'es2022'： Vite 开发期默认按接近 esnext 提供源码，而 Chromium 尚不能解析 TC39 标准装饰器语法。 instrument.ts 的 @logged / @measure 因此会在浏览器开发模式直接语法报错。把 target 对齐到 TypeScript 的 ES2022， 使开发与生产使用同一套降级规则；viteDevTransform.test.ts 把这条结论固化成回归测试，避免配置被“顺手清理”掉。

发布期：Rollup 分块与预算

R3F 的 Canvas 会注册完整 Three 命名空间，如果和应用代码打进同一个文件， 每次业务改动都会让用户重新下载整个 3D 引擎。 viteChunks.ts 因此把依赖按稳定度切成三块：

chunk内容字节预算
three-engineThree 引擎本体，变化最少700,000
react-three-runtimefiber、drei、three-stdlib、maath250,000
three-effectspostprocessing 与 Bloom 通道120,000
SceneCanvas按需加载的场景入口100,000
GLTFExporter只有导出时才需要的序列化器80,000
  • onlyExplicitManualChunks 阻止 Rollup 把共享的 React 依赖卷进延迟加载的场景块。
  • verify-desktop-bundle.ps1 在每次 pnpm build 后运行：每个前缀必须恰好一个 chunk、逐块不超预算、除引擎外没有超过 500,000 字节的块。
  • 它还检查 index.html 不能直接引用这些延迟 chunk——否则“代码分割”只是把一个大文件拆成几个同时下载的文件。
  • 预算是硬失败而不是警告：chunkSizeWarningLimit 只影响提示，真正的门禁在脚本里。

原生期：build.rs 与 Windows 版本资源

build.rs 是 Cargo 在编译 crate 之前运行的构建脚本。它做两件事： 先由 tauri_build 嵌入配置并生成 Windows 资源文件，再在 Windows 目标上把资源里的 FileVersion 与 ProductVersion 改写成 version.json 中的两段式公开版本，最后用 embed_resource 重新编译资源。

  • cargo:rerun-if-changed 指向 version.json，改版本号会触发重新构建而不是复用旧资源。
  • 脚本先校验 productVersion 恰好两段、全为数字、无前导零，非法值直接让构建失败。
  • 替换时统计命中次数，不等于一次就 panic。宁可构建失败，也不要产出“版本字符串只改了一半”的 EXE。
  • 这解释了为什么 Cargo 清单里的三段式兼容值不会出现在文件属性里：它在链接前就被替换掉了。

release profile 统一在根 Cargo.toml：lto 做跨 crate 内联， codegen-units = 1 牺牲编译并行度换取更好的优化，strip 去掉符号表以缩小体积。 这些只应用于发布构建，调试构建保持快速与可调试。

统一入口：justfile 是跨语言任务入口， just check / just bundle 包住 pnpm 与 cargo 两侧命令； 根 package.json 提供前端脚本，just check 再组合 pnpm 与 Cargo 检查；本机、CI 和发布复用这些命令， 而不是三份互相漂移的说明。

Versioning and dependencies

用一个两段式产品版本控制全部展示

用户要求的版本语义由两段数字表达，底层工具的格式要求则由机械兼容层承担。两者必须从一个文件派生并自动对照， 不能靠开发者手工记忆在多个清单中同步。

位置当前值原因
游戏 UI / 文档 / Changelog1.0唯一的产品版本
发布目录与交付文件名output/release/1.0面向玩家和发布人员
release manifestversion: 1.0不再暴露第二个版本字段
package.json / Cargo / Tauri构建兼容值（不展示）只满足工具解析要求
Windows EXE / 已安装的应用1.0安装器、主程序、卸载器与 DisplayVersion 一致

升级规则

  • 小的新功能：只增加第二段，不对玩家暴露额外补丁位。
  • 非常大的功能模块：增加第一段并把第二段归零。
  • 修复与内部重构：在同一候选内重新构建时用来源提交与哈希区分，不制造第二套产品版本。
  • 历史证据：原始测量 JSON 保持不可改写；当前产品资料只引用两段式版本。

依赖版本与产品版本不是一回事

React、Tauri、pnpm、WebView2 等依赖各自使用自己的版本政策；产品版本 1.0 不要求依赖采用相同数字。 依赖升级必须看 API、锁文件、公告、目标平台与实际回归。当前依赖解析还通过 override 固定 postcss 8.5.23 和 nanoid 3.3.18，用于消除已知安全公告；这类覆盖要在上游链路自然升级后再审慎移除。
