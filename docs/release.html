Windows release

从源码到可安装候选包的证据链

Tauri 构建会先产出 Rust/前端组合的 dream-builder.exe，再由 NSIS 生成当前用户安装包。 项目发布脚本在其上增加版本、源码状态、哈希、签名和文件集检查，防止拿错旧产物。

候选包的六个文件

  • Dream-Builder-Fantasy-Tree_1.0_x64.exe：便携入口；
  • Dream-Builder-Fantasy-Tree_1.0_x64-setup.exe：推荐 NSIS 安装器；
  • LICENSE.txt 与 README-zh-CN.md；
  • SHA256SUMS.txt：四个交付载荷的摘要；
  • release-manifest.json：schema 5、唯一产品版本、来源提交、源码树指纹、文件和签名状态。

源码指纹为何不只看 Git commit

构建先组装临时目录并运行独立校验，再替换正式候选目录；失败时保留上一份候选。 精确文件集检查包含隐藏文件、子目录和链接，发现任何额外条目都会停止，不会擅自替用户清空目录。 构建与验证复用 同一个源码指纹函数，防止两套算法漂移。

本地候选可能在 dirty worktree 构建；只记 HEAD 会把多个不同源码状态写成同一身份。脚本枚举受 Git 管理和未忽略文件， 对路径、大小与 SHA-256 形成排序索引，再计算整棵源码树指纹。产物生成后任何源文件变化都会让独立验证拒绝旧清单。

候选、生产和签名

构建成功只证明 EXE 与安装器可以生成；完整候选还要复制许可证、交付手册并生成清单。 手册的唯一源文件是 loop/product/release-runbook.md。 pnpm docs:verify 同时检查发布构建与验证脚本引用的文档路径；完整交付仍要执行 pnpm release:build 和 pnpm release:verify，两类检查不能互相代替。

类型允许状态可以怎样称呼
本地候选显式允许 dirty；EXE 必须明确 NotSigned；清单记录 sourceDirty开发候选，不得公开宣称正式版
干净候选干净提交、全部门禁、未签名可复核发行候选，仍非生产分发
生产包干净源码、证书库有效代码签名、时间戳、两份 EXE 均 Valid满足其余人工门槛后才可正式发布

签名检查使用宿主模块

发布脚本由 pnpm 再启动 PowerShell 时，会继承父进程的模块搜索路径。 PowerShell 7 的模块不能直接当作 Windows PowerShell 5.1 的内置模块加载；这可能导致签名命令自动加载失败。 因此两份发布脚本从 $PSHOME/Modules 显式加载当前宿主自己的安全模块， 继续执行真实的 Authenticode 检查，不修改用户的全局配置。模块路径继承规则见 Microsoft 的 PSModulePath 说明。

安装与卸载合同

release-install-state.ps1 在安装后检查唯一卸载项、 两段式版本 1.0、安装目录、主 EXE 和快捷方式实际目标；卸载后要求卸载项、程序目录、快捷方式和进程全部消失。 必须将安装检查输出的 InstallLocation 传给卸载检查的 -ExpectedInstallDirectory， 否则自定义位置残留时，单靠搜索默认目录可能误报“已经干净”。 使用 just 时，命令为 just release-verify-uninstalled "D:\Games\Dream Builder Fantasy Tree"； 将示例替换为实际安装路径，含空格的路径保留引号。 玩家数据可按升级/诊断政策保留，脚本只报告其存在，不读取或删除。完整手册见 release-runbook.md。

显示版本与升级比较各司其职

玩家继续看到两段式产品版本。安装器仅在比较时补足内部比较器要求的第三段，再判断同版重装或升级。 静默安装不经过版本选择页面，所以必须在安装前重新读取已装版本并执行检查；降级和无法确认的版本会被拒绝，避免旧程序覆盖新存档。 pnpm test:installer 编译并运行小型 NSIS 程序验证版本矩阵，完整发布构建会自动执行它。 小程序只能证明比较规则；完整模板还必须实际打包。包含插件调用的函数在编译时就要识别插件， 因而模板先注册插件目录，再加载自定义安装钩子，不能等到安装步骤之前才注册。 这些测试不安装游戏、不写卸载注册表，不能代替真实安装生命周期。
