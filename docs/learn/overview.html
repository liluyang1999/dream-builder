Product snapshot

当前项目究竟是什么

Dream Builder Fantasy Tree 的玩家名称是《智慧树之森》。它已从“可旋转观察的程序化智慧树” 演进为一个单人、离线、第三人称卡通森林盒庭：玩家探索三条支路，收集三枚光种，阅读森林记忆， 完成四拍方向净化，并看到中央智慧树、光照、地表、音景和章节门一起复苏。

  • 体验闭环标题、继续/新游戏、暂停、设置、章节结尾、继续漫游和安全退出。
  • 世界系统中央林地、蘑菇坡、溪流、遗迹门、碰撞、检查点和可重建装饰。
  • 玩家系统键鼠与标准手柄、相机相对移动、冲刺、重置、互动和方向谜题。
  • 反馈系统卡通光照、Bloom、粒子、程序化音景、进度声效、减少动态和高对比。
  • 可靠性v2 进度快照、v1 迁移、最近有效备份、损坏隔离、恢复提示和单实例。
  • 交付工程Windows EXE、双语 NSIS、哈希清单、来源指纹、签名门禁和卸载验收。

产品版本 1.0

玩家看到的版本采用两段式 主版本.功能版本，当前正式从 1.0 开始。版本契约、 本地 pnpm 存储约束、WebView2 策略、依赖安全修复与统一教学档案都归入这一个 1.0 产品版本。

单一显示口径

Cargo、npm 与 Tauri 的机器清单必须满足各自的 SemVer 语法，构建脚本会机械补足所需格式， 但不会把它当成第二套产品版本。游戏、资料、发布清单、Windows 文件属性与“已安装的应用” 都只显示 version.json 中的 1.0。

Architecture

总体架构：两个运行环境、三层规则

项目不是“Rust 把每一帧算好再交给网页”。正确分工是：Rust/Tauri 负责原生生命周期、持久状态、 确定性场景与低频边界；React/R3F 负责逐帧输入、运动、相机、呈现和界面。浏览器开发模式没有 Rust， 因而用 Web Worker 生成兼容场景，保持前端可以单独开发和测试。

玩家键鼠 / 手柄 / 指针
React界面、会话、状态编排
R3F / Three逐帧运动、相机、WebGL
Tauri IPC命令、事件、ACL
Rust生成、原生状态、存储
纯规则层游戏进度、方向谜题、输入归一化、运动与碰撞、选择 reducer。无 React、无 Three、无磁盘副作用。
适配层React hooks、GameplayController、PlayerController、treeApi、Worker client，把平台输入转换为纯规则动作。
呈现与副作用层R3F 场景、HUD、音频、Tauri 命令、持久化、文件导出、菜单、事件和安装器。

Tauri 桌面运行

pnpm tauri dev/build 创建原生窗口。Windows 内部由 Wry 驱动 WebView2； treeApi.ts 调用 Rust 命令并订阅事件。 场景数据由 Rust 生成，原生设置通过 Tauri Store 保存。

浏览器开发运行

pnpm dev 只启动 Vite。runtime.ts 判断没有 Tauri 后，让 fallback.worker.ts 在 Worker 中生成场景。它是开发容错路径，不是原生发布架构的替代。

核心不变量：相同 seed 的 Rust 生成必须确定；任何跨 IPC 的载荷必须经 Zod 校验； 渲染只能消费已提交的进度，不能自行发明“已经收集”或“已经净化”的状态；逐帧运动不经过 IPC。

Monorepo

pnpm workspace 与 Cargo workspace 为什么共处一仓

这是一个双工作区单仓：JavaScript/TypeScript 由 pnpm 管理，Rust 由 Cargo 管理。根目录提供统一版本、 锁文件、质量命令和发布入口，使一次跨边界改动可以在同一个提交里验证全部消费者。

配置的单一真相源

  • tsconfig.base.json 集中严格类型选项，各 TS 包只补充自身环境。
  • biome.json 同时承担格式化和静态检查，避免 ESLint/Prettier 规则漂移。
  • vitest.config.ts 用 projects 模型发现应用与共享包测试。
  • Cargo.toml 统一 edition、技术版本、lints 与 release profile。
  • version.json 是产品版本与技术兼容版本的唯一映射。
  • pnpm-workspace.yaml 同时约束成员、依赖覆盖和本地缓存位置。

pnpm 数据绝不写到磁盘根目录

storeDir: .pnpm-store
  cacheDir: .pnpm-cache
  virtualStoreDir: node_modules/.pnpm
  enableGlobalVirtualStore: false

内容寻址仓库位于 <repo>/.pnpm-store/，元数据缓存位于 <repo>/.pnpm-cache/，虚拟依赖树位于 <repo>/node_modules/.pnpm/。三者均被 Git 忽略， verify-pnpm-layout.ps1 会解析真实绝对路径， 拒绝盘符根目录、用户级全局虚拟仓库或越出项目的配置。

End-to-end flow

沿一条真实请求读完整系统

下面以“玩家进入世界并接近一枚光种”为主线，把启动、设置、场景、逐帧运动、状态提交、保存和反馈串起来。

  1. 启动：main.tsx 创建 React 根节点，错误边界包围应用；特殊查询参数可进入本地 M2 证据工具。
  2. 水合：App.tsx 先读取本地进度，再向 Rust 请求设置；设置确认前不抢先加载错误 seed。
  3. 场景：treeApi.loadScene(seed) 在 Tauri 中 invoke('generate_tree')，在浏览器中调用 Worker。返回值先经 treeSceneSchema 验证。
  4. 呈现：SceneCanvas.tsx 把场景、世界、光照、粒子和后处理挂入 R3F Canvas。
  5. 输入：键盘、手柄被归一化为移动与动作意图；playerMotion.ts 根据相机水平前向、时间步和碰撞布局算新位置。
  6. 接近：GameplayController.tsx 只负责距离检测与输入适配，触发 reveal-seed 或 collect-seed 动作。
  7. 提交：reduceGameProgress 检查合法转换，返回不可变新快照；非法跳转直接保持原状态。
  8. 持久化：Zustand store 只在真实进度改变后写 v2 快照，写入前保留上一份有效快照作为备份。
  9. 反馈：R3F 根据已提交快照播放光种消散和树木复苏；AudioDirector 根据进度差异播放声效；QuestPanel 更新目标。
  10. 原生事件：Rust 周期性发出 magic-field，前端放进 ref，粒子在 useFrame 内读取，不让 React 每帧重渲染。
为什么强调“提交”：视觉动画可能被跳帧、卸载或减少动态设置缩短；如果动画本身决定进度， 存档与 UI 会失真。这里先由纯状态机完成原子转换，再让所有视觉与声音成为该事实的消费者。
