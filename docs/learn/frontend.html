TypeScript + React 19

前端：用严格类型把框架留在边缘

TypeScript 不是给 JavaScript 加注释，而是让边界、状态转换和组件契约在编译期可证明。 React 则负责把这些数据映射为界面和生命周期；高频游戏数学留在纯函数与 R3F 帧循环中。

严格编译选项

strict、noUncheckedIndexedAccess、 exactOptionalPropertyTypes、noImplicitOverride 与 verbatimModuleSyntax 同时开启。数组索引因此是 T | undefined， 可选属性也不能用“显式 undefined”冒充缺失。

unknown 后再收窄

IPC、JSON 文件、本地存档和性能证据都是不可信数据。它们先保持 unknown， 再由 Zod 或专用解析器验证。禁止用 as SomeType 跳过边界检查。

可辨识联合

GameProgressAction、SelectionAction、Worker 协议和 SceneLoadResult 都用字面量字段区分分支。switch 让新增状态暴露未处理点。

标准装饰器

instrument.ts 的 @logged 和 @measure 使用 TC39 标准方法装饰器，为 IPC 加日志与计时， 不依赖旧式 experimentalDecorators。

React 的职责分层

入口main.tsx 只决定挂载哪个根应用，并安装 StrictMode 与错误边界。
编排App.tsx 管设置水合、场景加载、原生订阅、导出、菜单和跨系统回调。
状态state/store.ts 暴露选择器和动作，委托纯 reducer；组件不直接改内部对象。
适配Controller 组件把浏览器事件、手柄轮询、接近判定和 R3F ref 转换为领域动作。
呈现UI 与 Scene 组件根据 props/store 切片渲染，避免承担持久化或业务决策。

Hooks 在这里解决什么问题

  • useEffect 管理外部系统同步：IPC 请求、事件监听、键盘监听、设置持久化，而不是计算可派生值。
  • useRef 保存每帧读取的魔法场、场景命令 API、玩家位置与最新回调，更新它们不会触发 React 树重绘。
  • useMemo 缓存昂贵且纯的几何/实例矩阵；依赖必须真实完整，不能拿空数组“冻结”错误值。
  • useCallback 只在回调身份会影响订阅或子组件时使用；不把它当作无条件性能装饰。
  • StrictMode 会故意重复挂载 effect。asyncSubscriptionScope.ts 专门处理“监听 promise 尚未返回，组件已经卸载”的竞态。
错误边界的边界：React Error Boundary 捕获渲染和生命周期错误，但不会自动捕获事件处理器、 异步 promise 或 Rust 崩溃。后者必须在调用点处理，并由日志、错误状态或原生 panic hook 提供证据。

State, save, input

状态、存档、输入与运动为何要分开

游戏最容易失控的地方，是把按键、位置、任务、动画和存档塞进同一个组件。 本项目把“瞬时输入”“逐帧运动”“持久进度”“界面会话”和“原生设置”拆成不同寿命的状态。

状态种类拥有者寿命与示例
输入意图playerInput.ts / Gamepad一帧或一次按下；移动向量、互动、冲刺、暂停。
运动状态PlayerController.tsx连续帧；位置、速度、朝向，由纯运动函数推进。
游戏进度gameProgress.ts + Zustand跨会话；光种、节点、树阶段、门、检查点、记忆。
会话 UIZustand当前运行；标题/游玩/暂停、覆盖层、选择、警告。
用户设置前端 store + Rust Store跨启动；主题、画质、音量、相机、无障碍。

进度状态机的不变量

light seed: hidden → revealed → collected
  three collected: node dormant → ready
  puzzle open: ready → cleansing
  success: cleansing → restored + treeStage 1 + gateUnlocked
  cancel/failure: cleansing → ready（不扣光种）

gameProgress.ts 用字面量联合、 Record<LightSeedId, LightSeedState> 和纯 reducer 表达这些规则。 解析旧存档时重新计算 collectedCount，并验证树阶段和门状态必须与净化状态一致； 这能拒绝“字段看似合法，但组合互相矛盾”的快照。

存档恢复策略

  1. 优先读取 dream-builder.progress.v2，通过完整不变量校验才接受。
  2. 主快照损坏时，把原始文本隔离到 corrupt key，再尝试最近一份有效 backup。
  3. 只有主快照不存在时才迁移 v1；迁移补上检查点与记忆字段，不迁移中途 cleansing 状态。
  4. 正常写入前先把上一份有效主快照变成 backup；“开始新旅程”则原子替换并清理旧备份。
  5. Storage 不可用或写失败时保持当前会话可玩，并通过 UI 提示，不能静默假装已经保存。

运动与碰撞

playerInput.ts 把 WASD、方向键和手柄轴统一成 归一化意图；playerMotion.ts 将它转换到相机水平坐标系， 按加速/减速和最大步长推进。世界边界、圆形障碍与矩形障碍来自 forestLayout.ts，同一份布局同时被碰撞和呈现消费， 避免“看见的墙”和“撞到的墙”漂移。

为什么不用物理引擎

当前只有平面行走、静态障碍和显式边界。纯数学碰撞更小、更确定、更易测；出现斜坡、动态刚体或大量碰撞前，引入物理引擎只会增加同步成本。

为什么相机不进 Rust

相机和玩家运动每帧更新，把它们经 IPC 往返会增加延迟与序列化负担。Rust 负责低频、可持久、可重放的数据，帧循环留在 WebView。
