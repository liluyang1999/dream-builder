Performance evidence

性能不是一个 FPS 数字，而是一条可复核证据链

场景必须在真实 Tauri/WebView2 目标设备上持续运行，才能代表交付体验。项目内置记录器只保存有界聚合， 同时避免收集玩家路径或逐帧行为数据。

  • PerformanceProbe 在帧循环读取帧间隔与 Three renderer 统计。
  • PerformanceMetricsRecorder 用固定 0.5ms 直方图估计分位数，不保留无限增长的原始帧数组。
  • 状态 marker 最多 128 个、phase 最多 32 个；名称与环境字符串有长度上限，导入报告也重新校验。
  • 报告给出平均 FPS、1% low 等价值、P50/P95/P99、最长帧、慢帧比例、draw calls、三角形和可用堆峰值。
  • scene-load 与 cleansing 单独分段，不能用稳态平均值掩盖加载或净化尖峰。
  • 浏览器主循环只能观察 CPU/呈现间隔，不能直接得到 GPU frame time；需要 GPU 指标时另用目标设备分析器。

直方图把相近帧间隔放入同一个桶，桶的上界可能略高于实际采样值。因此分位数估计还要以实际观测的最长帧为上限， 保持 P50 ≤ P95 ≤ P99 ≤ 最长帧。这些分位数仍是有限精度的估计，但导出的报告应当自洽， 不能出现“99% 的帧不超过的时间，比所有帧中最长的还长”。

平均流畅，也要检查第一次操作

十分钟的平均值可能掩盖一次两秒的停顿。应分别观察首次启动、第一次遇到新物体，以及同一进程中的再次游玩。 CPU 采样可以帮助区分数据生成、场景对象创建和图形程序编译；不能只凭“重新生成时卡住”就认定后端计算太慢。

Three 会把点光源数量写入着色器程序的配置。若拾取物或任务状态不断增加、移除灯，第一次遇到新数量时可能需要重新编译。 本项目让这类灯保持挂载，用强度零表示暂时不发光，避免进度变化反复改变灯的数量；物体本身仍按原规则显隐。 零强度的灯仍占计算预算，因此这项取舍必须结合真实冷启动和稳态帧率复测，不能只靠单元测试判断快慢。

scene-load 从发起请求开始，在数据就绪后再等待一秒结束；这个观察窗口不等于 GPU 已完全准备好。 如果主线程停顿，阶段结束与下一帧的先后顺序也会影响分段归属，所以要同时查看整段最长帧和操作现场。

已归档事实

目标 Windows 设备已有十分钟原生性能报告，覆盖场景加载与净化，并通过当前 M2 帧率预算。

仍未替代的事实

真实性能通过不代表五位新玩家能理解目标；自动化和证据工作台都不能代替真人无提示观察。
