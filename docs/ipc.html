IPC contract

IPC：跨语言边界必须同时有静态类型和运行时证据

TypeScript 类型在运行时会被擦除，Rust 类型也不会自动保护已经变成 JSON 的数据。 因此 IPC 的正确模型是：Rust 按 serde 合约序列化，前端先把载荷视为 unknown， 经 Zod 成功解析后才进入应用核心。

事件与请求的区别

命令是请求/响应，适合“给我一个场景”“保存这份设置”；事件是后端主动推送，适合周期魔法场和原生菜单。 events.rs 发出 magic-field， menu.rs 把菜单 id 转成 menu:<id>。 每个前端事件 payload 仍要校验；事件并不因为来自本进程就自动可信。

修改 wire 格式时的四方同步

  1. Rust domain struct 与 serde rename/enum 表示；
  2. packages/ipc-contracts 的 Zod schema 和推导类型；
  3. 浏览器 Worker 回退生成器与协议；
  4. Rust 序列化集成测试、Zod 契约测试和前端消费者测试。
常见错误：只改 TS interface 不会改变运行时校验；只改 Rust 字段会让旧前端回退； 用 as TreeScene 会把协议错误推迟到渲染深处，变成更难诊断的 WebGL 故障。

第二条边界：主线程与 Web Worker

浏览器开发模式没有 Rust，场景改由 Worker 生成。这是本项目的第二个消息边界， 它和 IPC 面对同一个问题：异步、无共享内存、只能传结构化克隆的数据。 解决方式也同构——先定义协议，再让客户端把消息还原成 Promise。

protocol.ts

请求 { id, seed }、响应 { id, scene }。 id 是关联键：postMessage 没有返回值，多个并发请求的响应 只能靠回声 id 找到自己的 resolver。

fallbackClient.ts

主线程客户端：懒创建 Worker、用 Map<id, resolve> 登记在途请求， 收到消息后取出并兑现对应 Promise，对调用方只暴露 createFallbackScene(seed): Promise<TreeScene>。

  • Worker 不可用时（jsdom 单测或任何非 DOM 环境）直接同步调用 fallbackTree.ts，返回同样的 Promise，因此调用方不需要分支。
  • 把生成放进 Worker 的收益是不阻塞主线程：几千个分段的几何计算发生在另一个线程，UI 仍然响应。
  • 代价是数据要跨线程克隆，所以 Worker 只用于低频的整场景生成，逐帧数据绝不走这条路。
  • Worker 返回的场景同样要过 treeSceneSchema。同进程不等于可信——回退生成器一样会写错。
