# Loop Engineering 概念与本项目的循环纪律

「Loop Engineering」在本项目里指一件具体的事：**开发以可复核的闭环推进，每一轮都必须留下
能被别人重新验证的证据，而不是留下一句「我测过了」。**

AGENT 参与开发时最容易犯的错误不是写错代码，而是**把"看起来完成"当成"已经完成"**。
下面这套纪律就是为了让这个错误在提交之前被拦下来。

## 一、一轮循环的六个阶段

```text
        ┌─────────────────────────────────────────────┐
        │                                             │
   意图 → 边界 → 实现 → 门禁 → 证据 → 状态 ──────────┘
    │      │      │      │      │      │
    │      │      │      │      │      └ 更新 progress.md；未闭合的仍标为未闭合
    │      │      │      │      └ 归档到 evidence/，只追加不改写
    │      │      │      └ 运行全部适用门禁，读退出码而不是读输出片段
    │      │      └ 最小、可回滚、与既有架构一致的改动
    │      └ 写下验收标准与不做什么，再动代码
    └ 从 product/ 确认要解决的问题，而不是从单个源文件猜
```

每个阶段都可能回到上一阶段。**唯一不允许的是跳过「门禁」直接进入「状态」**——那等于用意图
替换证据。

## 二、四条硬规则

### 1. 自动化通过 ≠ 可以发布

本项目刻意把门槛分成两类，并且**永远分开记账**：

| 类别 | 例子 | 谁能判定 |
|---|---|---|
| 自动化门禁 | `pnpm check`、`cargo clippy`、哈希与清单校验 | 机器，可重复 |
| 外部人工门槛 | 五名首次接触玩家的无提示观察、实体手柄听测、干净账户安装升级、受信任代码签名 | 只能由人在真实环境完成 |

绿色 CI 是「候选包可以进入人工验收」的前提，**不是**「可以发布」的结论。
把未完成的人工门槛写成已通过，是本项目定义中最严重的错误。

### 2. 证据只追加，不改写

`evidence/` 中的测量 JSON、哈希、时间戳与设备信息一律保持原样。
理由是可复核性：一旦允许回头修改历史数值，任何结论都不再能被独立验证。

- 文件移动时只更新**指针**（如清单里的 `relativePath`），因为身份由 SHA-256 承担，不由路径承担。
- 旧证据中的历史版本号、旧提交哈希保持原样，不为了「看起来一致」而改。
- 需要新结论时**新增**一份证据，并说明它与旧证据的关系。

### 3. 单一真相源，禁止第二份

同一个事实只能有一个可写位置，其余位置全部由它派生或指向它：

| 事实 | 唯一真相源 |
|---|---|
| 产品版本 | [`version.json`](../version.json) 的两段式 `productVersion` |
| 跨语言 wire 格式 | Rust domain struct + [`packages/ipc-contracts`](../packages/ipc-contracts/src/index.ts) 的 Zod schema |
| 世界布局与碰撞 | [`forestLayout.ts`](../apps/desktop/src/game/forestLayout.ts) |
| 游戏进度规则 | [`gameProgress.ts`](../apps/desktop/src/game/gameProgress.ts) 的纯状态机 |
| 产品范围与验收 | [`product/release-1.0.md`](product/release-1.0.md) |
| 当前进展 | [`progress.md`](progress.md) |
| 技术概念与源码地图 | [`docs/`](../docs/index.html) |

发现同一事实出现在两个可写位置时，正确动作是**消除其中一个**，而不是同步它们。

### 4. 教学与工程分离

`docs/` 写「为什么这样组织、概念是什么、代码在哪里」——追求长期稳定。
`loop/` 写「要做什么、到了哪一步、证据是什么」——随迭代改变。

混写的代价很具体：读者无法判断一段文字是长期结论还是当前状态，于是两种内容都开始不被信任。

## 三、每一轮必须回答的检查清单

改动完成、准备提交前，逐条回答：

- [ ] 这次改动解决的问题，在 `product/` 或用户请求中有明确出处吗？
- [ ] 我运行了**全部适用**门禁，并确认了退出码，而不是只看输出片段？
- [ ] 新增的规则有对应测试吗？缺陷修复有先失败后通过的回归测试吗？
- [ ] 我新加的门禁**被反向测试过**吗（故意破坏一次，确认它真的会失败）？
- [ ] 跨边界改动是否同步了 Rust domain、Zod schema、浏览器回退与两侧测试？
- [ ] 有没有把未完成的人工门槛写成已完成？
- [ ] `progress.md` 与受影响的产品文档更新了吗？
- [ ] 提交范围是否只包含本次意图内的文件？

## 四、常见失效模式

| 失效模式 | 表现 | 正确做法 |
|---|---|---|
| 用通过掩盖范围 | 「测试全绿」但需求只做了一半 | 完成全部范围，或明确说明未做的部分与原因 |
| 用自动化替代真人 | 用组件测试断言「可玩性通过」 | 可玩性只能由 `product/m2-playtest.md` 的观察产生 |
| 门禁失败就调阈值 | 放宽预算、跳过测试、删断言 | 先判断产品合同是否真的改变，再决定 |
| 无声截断 | 只处理前 N 项却报告为全部完成 | 明确 log 被丢弃的部分 |
| 新增门禁却从未失败过 | 写了检查但从未验证它有效 | 反向测试：故意破坏一次，确认报错 |
| 记录漂移 | 代码改了，文档与状态没改 | 同一提交内更新文档与 `progress.md` |

## 五、这套纪律在仓库里的落点

| 概念 | 强制它的机制 |
|---|---|
| 自动化门禁 | `pnpm check` 九阶段 + `cargo fmt/test/clippy` |
| 版本单一真相源 | `pnpm version:verify` |
| 最小权限与浏览器边界 | `pnpm desktop:verify-security` |
| 教学覆盖完整性 | `pnpm docs:verify`（含全部源码模块覆盖） |
| 工程记录完整性 | `pnpm loop:verify` |
| 证据不可改写 | `pnpm m2:verify` 复算哈希与时长 |
| 依赖存储不外溢 | `pnpm pnpm:verify-layout` |
| 产物身份 | `pnpm release:verify` 的源码树指纹与精确文件集 |

门禁的价值在于**它会失败**。任何一条从未失败过、也没被反向测试过的检查，都应假定它没有生效。
